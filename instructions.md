## 1. Problem statement

Build an AI-powered meeting assistant that turns a recorded meeting into an accurate transcript and a usable written record. The system must transcribe the audio, refine domain-specific terminology in the transcript, and generate structured meeting minutes, key decisions, and actionable tasks through a coordinated multimodel pipeline.

The application must present the raw transcript, refined transcript, and generated record in an interactive interface. Its outputs must reflect what was said in the recording; where a task owner or deadline was not stated, the system must leave that detail unspecified rather than invent it.

## 2. Objectives

* Convert recorded meeting speech into a readable transcript using a speech-to-text model.

* Use a language model to correct transcription errors in domain-specific terms while preserving the meaning of the conversation.

* Use a separate language model to produce structured minutes, decisions, and action items.

* Orchestrate the models into one reliable end-to-end workflow with an interactive interface and downloadable results. *(Note: Detect the ArUco marker (DICT_4X4_50, 0.24 m) on each clue board and decode the QR code beside it.)*

## 3. Requirements

*(Note: Each board shows an ArUco marker (left) and a QR code (right). The QR code contains one line:)*

| Model type | Required role | 
| ----- | ----- | 
| **Speech-to-text model** | Transcribe spoken content from the uploaded meeting recording. | 
| **Language model for transcript refinement** | Correct likely transcription errors, especially domain-specific terms, using the meeting context. | 
| **Language model for meeting documentation** | Generate structured minutes, key decisions, and action items from the refined transcript. | 

The two language-model roles must be implemented as distinct processing stages. Teams may choose the models, implementation language, orchestration approach, and interface technology. The selected models and their roles must be identified in the submission.

* The application must accept an English-language meeting audio file and process it from upload through final output in one run.

* The application must retain both the raw and refined transcripts and produce a structured final record.

* The application must handle unsupported, empty, or unreadable files with a clear error message.

* Outputs for a new recording must be generated by the pipeline: prewritten or hardcoded results do not satisfy the requirement.

## 4. Functional requirements

### Audio input and transcription

Allow the user to upload a meeting recording. Convert its spoken content to a raw transcript and make that transcript visible for review. If the audio cannot be processed, explain the problem in the interface.

### Domain-aware transcript refinement

Pass the raw transcript to a language model tasked with correcting plausible recognition errors in technical terms, acronyms, and other domain-specific language. Preserve the speaker's intended meaning, including names, numbers, negation, and commitments. Show the refined transcript separately from the raw transcript so users can compare them.

### Meeting minutes and task extraction

Pass the refined transcript to a separate language model. Produce a concise meeting summary, organized minutes, a list of key decisions, and a list of actionable tasks. Each task must state the work to be done and include an owner or deadline only when the recording provides one. Do not present a proposal as an agreed decision or an unstated assignment as a confirmed task.

### Workflow and interface

Run transcription, transcript refinement, and meeting-documentation generation in the stated order as one workflow. Provide an interactive interface in which a user can upload audio, start processing, inspect the transcripts and final results, and download the outputs. Show clear processing or failure status.

## 5. Evaluation

Submissions will be assessed on a previously unseen English-language meeting recording as well as the submitted demonstration and documentation. The rubric totals 100 points.

| Criterion | Points | Evidence assessed | 
| ----- | ----- | ----- | 
| **Speech transcription** | 20 | Completeness and accuracy of the raw transcript, including names, terminology, numbers, and negation. | 
| **Transcript refinement** | 20 | Correction of genuine terminology errors while preserving the content and intent of the recording. | 
| **Minutes and decisions** | 25 | Accurate, concise minutes and correct identification of agreed decisions without invented claims. | 
| **Action items** | 15 | Complete and actionable task descriptions, with owners and deadlines reported only when stated. | 
| **End-to-end application** | 15 | Distinct model stages, successful processing of a new recording, usable interface, exports, and clear error handling. | 
| **Submission quality** | 5 | Clear setup instructions, model identification, and sample outputs that match the demonstration. | 

Reviewers will compare the generated transcript, minutes, decisions, and tasks against the recording and check that the complete pipeline works on new audio.

## 6. Output requirements

The application must display and allow download of the following outputs for each processed recording:

| Output | Required contents | 
| ----- | ----- | 
| **Raw transcript** | The speech-to-text result before language-model refinement. | 
| **Refined transcript** | The transcript after domain-aware terminology correction. | 
| **Meeting minutes** | A concise summary and organized account of the main discussion points. | 
| **Key decisions** | A structured list of decisions reached in the meeting, an empty list if none were reached. | 
| **Action items** | A structured list of tasks, with description and any stated owner or deadline; an empty list if none were assigned. | 

The meeting record must be available in a human-readable format and in a machine-readable structured format. Both formats must convey the same decisions and tasks. Missing owners or deadlines must be shown as unspecified, not guessed.

## 7. Deliverables

* A source repository or archive containing the complete application, prompts or model instructions, dependency information, and a README with setup and run instructions.

* A working interactive application that can process a new meeting recording from audio upload to downloadable results.

* A short technical description identifying the speech-to-text model and the two language models, explaining each model's role and how outputs move between stages.

* At least one meeting recording that may be shared, together with the raw transcript, refined transcript, minutes, decisions, and action items generated by the application.

* A demonstration showing an end-to-end run and the resulting outputs.

## 8. Antigravity Prompting Tips & Workflow

To get the best results from the Antigravity agent, avoid asking it to build the entire system in one prompt. Instead, guide it through these progressive phases:

### Phase 1: Setup & UI Framework
*   **Prompt Example:** *"Read this problem statement. Set up a Python virtual environment and create a `requirements.txt` file. Then, build a basic Streamlit app with a file uploader that only accepts audio files (mp3, wav). Add clear error handling if the user uploads an invalid file type, as required by the 'Audio input and transcription' section."*

### Phase 2: Speech-to-Text Integration
*   **Prompt Example:** *"Update the Streamlit app to include a 'Process Audio' button. When clicked, pass the audio file to the `openai-whisper` library (use the 'base' model to save compute for now). Display a loading spinner while processing, and output the raw transcript to the UI. Ensure you handle temporary file storage for the uploaded audio correctly."*

### Phase 3: The Refinement Model (LLM Stage 1)
*   **Prompt Example:** *"We need to add the first LLM stage: Transcript Refinement. Use the Google GenAI SDK (read the API key from a `.env` file). Write a strict system prompt instructing the model to fix domain-specific terminology without changing the speaker's original intent or hallucinating details. Add a side-by-side view in Streamlit to compare the raw and refined transcripts."*

### Phase 4: Action Extraction (LLM Stage 2) & Export
*   **Prompt Example:** *"Now build the final pipeline stage. Take the refined transcript and pass it to a second LLM call. Instruct the model to output a strictly formatted JSON object containing: `summary`, `minutes`, `decisions`, and `action_items`. Remind the model: if no deadline or owner is stated for an action item, it MUST output 'unspecified'. Finally, parse this JSON into the UI and add a button to download all results as a text file."*

### General Best Practices
*   **Prevent Hallucinations:** Explicitly tell the agent: *"Do not hardcode any transcript results. The data must flow dynamically from the Whisper output to the LLMs."*
*   **Dependencies:** Remind the agent to update `requirements.txt` every time it installs a new library (like `streamlit`, `whisper`, `ffmpeg-python`, or `google-genai`).
*   **Debugging:** If the agent hits a roadblock (e.g., FFmpeg isn't installed on the system), ask it to: *"Check the terminal logs for the FFmpeg error and write a bash script to install the necessary system dependencies."*
